# 工地管理小程序 · 功能研究与产品设计

> 本文档回答一个问题：**一家家装/整装公司的 ERP，究竟需要哪些功能？**
> 内容基于对国内主流装企管理软件（[小叮当 ERP](http://m.xddsoft.com/newsshow_22338.html)、[掌赋](https://baike.baidu.com/item/%E6%8E%8C%E8%B5%8B/23705746)、[一装 ERP](https://www.eim.1zerp.com/web/page_index.html)、[装修密码](https://apps.apple.com/cn/app/%E8%A3%85%E4%BF%AE%E5%AF%86%E7%A0%81%E8%A3%85%E4%BF%AE/id1642674503)等）的产品拆解与行业调研整理。

---

## 一、行业特征决定了系统形态

装修行业与传统制造/零售业差别很大，管理难点集中在五件事：

| 难点 | 具体表现 | 系统要解决什么 |
|---|---|---|
| **链条长** | 获客 → 量房 → 设计 → 报价 → 签约 → 施工 → 主材 → 验收 → 售后，跨度 3~12 个月 | 全流程一条主线，不能断点 |
| **工种多** | 水电工、泥瓦工、木工、油漆工、安装工交叉进场 | 工序节点标准化 + 责任到人 |
| **节点细** | 一个工地 10~20 个验收节点，靠微信口头汇报 | 节点可打卡、可拍照、可追踪 |
| **变更多** | 增项减项频繁，扯皮高发 | 变更签证必须留痕、必须客户确认 |
| **钱难收** | 按进度分期收款，做完了忘记收钱是现金流杀手 | 收款计划自动提醒、逾期预警 |

由此得出核心设计原则：**以「项目（工地）」为中心轴，向前接客户与合同，向后接材料、施工、财务、售后。**

## 二、完整功能地图

一线装企 ERP 通常由 7 大模块构成：

```
┌─────────────────────────────────────────────────────────────┐
│                      经营驾驶舱（报表）                        │
│        回款 / 成本 / 毛利 / 人效 / 转化率 / 工期达标率          │
└─────────────────────────────────────────────────────────────┘
        ▲              ▲              ▲              ▲
┌───────┴────┐ ┌───────┴────┐ ┌──────┴─────┐ ┌─────┴──────┐
│  ① 客户 CRM │ │ ② 报价预算  │ │ ③ 合同收款  │ │ ④ 施工管理  │
│  线索/跟进  │ │ 量房/清单  │ │ 签约/分期  │ │ 节点/巡检  │
│  漏斗/转化  │ │ 主材/辅材  │ │ 开票/回款  │ │ 变更/验收  │
└────────────┘ └────────────┘ └────────────┘ └────────────┘
        ▲              ▲              ▲              ▲
┌───────┴──────────────┴──────────────┴──────────────┴───────┐
│  ⑤ 材料采购          ⑥ 财务成本           ⑦ 售后维保         │
│  请购/下单/入库/使用   支出/审批/成本归集    报修/派工/回访   │
└─────────────────────────────────────────────────────────────┘
```

### ① 客户 CRM（获客与转化）

| 功能点 | 说明 | 关键价值 |
|---|---|---|
| 线索登记 | 姓名、电话、来源渠道、小区、面积、预算 | 销售撞单、线索丢失是第一大痛点 |
| 来源渠道管理 | 抖音、小红书、转介绍、楼盘、门店、平台 | 判断哪个渠道值得投钱 |
| 跟进记录 | 每次电话/微信/到店/量房都留档 | 销售离职，客户资料不流失 |
| 意向分级 | A/B/C/D 四级 | 精力优先投给高意向 |
| 销售漏斗 | 新线索→跟进中→已量房→已报价→已签约 | 看出卡在哪一环 |
| 下次跟进提醒 | 到期待办 | 避免线索「放凉」 |
| 战败/流失原因 | 价格、工期、竞品 | 反向优化报价与话术 |

### ② 报价预算（最容易出利润漏洞）

| 功能点 | 说明 |
|---|---|
| 量房数据 | 面积、户型、承重墙、管道位置，含现场照片 |
| 报价模板 | 按户型/风格/套餐预设清单，避免每次从零编 |
| 清单式报价 | 分类（基础/水电/泥瓦/木工/油漆/主材/安装），每项含规格、单位、数量、单价 |
| 费用构成 | 明细小计 + 管理费（按比例）+ 设计费 − 优惠 = 总价 |
| 单方造价 | 元/㎡，用于横向比价和毛利测算 |
| 报价审批 | 低于底价需老板审批，防止销售乱打折 |
| 版本管理 | 客户改需求后出 v2、v3，避免口头承诺无据 |
| 一键转合同 | 报价确认后直接生成合同，金额自动带入 |

> **关键洞察**：装企报价常出现「漏项」，签完合同才发现防水、垃圾清运、成品保护没算钱。清单模板化是唯一解法。

### ③ 合同与收款（现金流命门）

| 功能点 | 说明 |
|---|---|
| 合同档案 | 合同号、金额、签约日期、开工/竣工日期、付款方式 |
| **按进度分期** | 首付 30% → 水电验收 30% → 泥木验收 30% → 竣工 10% |
| 收款计划自动生成 | 分期金额按比例自动算，不用手工乘 |
| 收款提醒 | 到期前提醒，逾期标红 |
| 实收登记 | 金额、方式（微信/支付宝/银行/现金/刷卡）、日期、经办人 |
| 欠款台账 | 每份合同「已收 / 待收 / 逾期」一目了然 |
| 关联项目 | 合同 ↔ 工地双向跳转 |

### ④ 施工管理（系统的核心）

| 功能点 | 说明 |
|---|---|
| **标准工序模板** | 开工交底 → 拆改 → 水电 → 水电验收 → 防水闭水 → 瓷砖 → 木工 → 腻子 → 油漆 → 主材安装 → 竣工验收 |
| 节点权重 | 每个节点占整体进度百分比，进度自动加权算出 |
| 节点状态流转 | 未开始 → 进行中 → 已完成，超期自动标记「已逾期」 |
| 计划 vs 实际 | 计划起止 vs 实际起止，工期偏差可量化 |
| 现场照片 | 每个节点上传施工照片（演示版留了数据结构） |
| 巡检/验收 | 隐蔽验收、中期验收、竣工验收，逐项勾选合格与否 + 整改意见 |
| 变更签证 | 增项必须生成签证单，客户确认后才施工、才计费 |
| 工期预警 | 剩余天数、逾期节点数 |
| 角色分工 | 项目经理、设计师、监理各司其职 |

> **关键洞察**：施工节点是装修 ERP 与通用项目管理软件最大的差异点。装修的特殊性在于「隐蔽工程」——水电、防水一旦封起来就无法复核，所以验收留痕（照片 + 检查项 + 签字）具有法律与质量双重意义。

### ⑤ 材料采购

| 功能点 | 说明 |
|---|---|
| 材料清单 | 主材（瓷砖/地板/门/橱柜/洁具）、辅材（水泥/黄沙/防水/腻子）、设备（空调/新风）、软装 |
| 采购状态 | 待采购 → 已下单 → 在途 → 已入库 → 已使用 |
| 供应商管理 | 单价、结算方式、供货准时率 |
| 用量核算 | 按面积/图纸算量，避免多买浪费、少买停工 |
| 到场登记 | 到货日期、验收人，避免「说到了其实没到」 |
| 损耗率分析 | 石膏板、瓷砖等主材损耗异常要复盘 |

### ⑥ 财务与成本

| 功能点 | 说明 |
|---|---|
| 支出登记 | 主材采购、辅材、人工费、运输费、管理费、设计费 |
| 费用审批 | 项目经理提交 → 老板审批 → 财务支付 |
| 成本归集 | 所有支出自动归到项目成本 |
| **项目毛利** | 合同额 − 实际成本 = 毛利，实时看 |
| 预算 vs 实际 | 超支预警，避免「装完才知道亏了」 |
| 现金流 | 本月收款、本月支出、净现金流 |
| 应收应付 | 客户欠款、供应商欠款 |

### ⑦ 售后维保

| 功能点 | 说明 |
|---|---|
| 报修工单 | 客户报修 → 登记 → 派工 → 上门 → 完成 |
| 保修期管理 | 水电 5 年、防水 5 年、其他 2 年（行业惯例） |
| 处理时间轴 | 全部处理记录留痕，避免扯皮 |
| 优先级 | 普通 / 紧急 / 特急（漏水是特急） |
| 回访满意度 | 影响转介绍率 |
| 问题分类统计 | 墙面开裂、防水渗漏高发 → 反推施工质量问题 |

### ⑧ 经营驾驶舱

| 指标 | 用途 |
|---|---|
| 合同总额 / 已收款 / 待收款 | 规模与现金流 |
| 项目毛利排行 | 哪类工地赚钱 |
| 项目经理人效 | 谁的工期达标、投诉少 |
| 客户来源转化率 | 投放决策 |
| 近 6 个月收支趋势 | 判断淡旺季 |
| 工期达标率 | 交付能力 |

### 演示版有意省略的部分

| 功能 | 原因 | 若上线如何补 |
|---|---|---|
| 真实后端 | 用本地存储模拟，保证零配置可运行 | store.js 内方法改为 wx.request，页面不动 |
| 图片上传 | 需要云存储与真实工地照片 | 接入 wx.uploadFile + 云开发存储 |
| 3D 设计/效果图 | 属于另一类专业软件（酷家乐等） | 通过 H5 或跳转第三方对接 |
| 电子签章 | 需要 CA 资质 | 对接法大大/e 签宝 |
| 消息推送 | 需要服务号模板消息 | 订阅消息 + 后端定时任务 |
| 多门店/多组织 | 数据模型需加 org 层级 | 表增加 tenant_id |
| 财务开票 | 需对接税控 | 对接电子发票平台 |

## 四、数据模型关系

```
用户(User)
  ├─ 负责 → 客户(Customer)
  ├─ 负责 → 项目(Project)
  └─ 处理 → 售后(Aftersale)

客户(Customer)
  ├─ 1:N → 跟进记录(Follow)
  ├─ 1:N → 报价单(Quote) ──── 1:N → 报价明细(QuoteItem)
  ├─ 1:N → 合同(Contract) ─── 1:N → 分期(ContractPlan) ─── 1:N → 收款(Receipt)
  ├─ 1:1 → 项目(Project)
  └─ 1:N → 售后(Aftersale)

项目(Project)  ← 业务核心轴
  ├─ 1:N → 施工节点(Node)
  ├─ 1:N → 巡检(Inspection) ─── 1:N → 检查项(InspectionItem)
  ├─ 1:N → 变更签证(Change)
  ├─ 1:N → 材料(Material)
  ├─ 1:N → 支出(Expense)
  └─ 1:1 → 合同

待办(Todo) ── 指向 → 支出/合同分期/报价/变更/售后
```

**核心金额等式**：
- 报价：`明细合计 + 管理费(明细×费率) + 设计费 − 优惠 = 合同额`
- 项目：`合同额 − 累计成本 = 毛利`，`已收款 / 合同额 = 回款率`
- 进度：`Σ(已完成节点权重) + Σ(进行中节点权重 × 50%)`

## 五、为什么这样设计（设计决策记录）

1. **以项目为中心而非以合同为中心** —— 修理工地是日常操作对象，合同只在签约和收款时用。员工打开 App 90% 是为了看工地。

2. **节点权重 + 自动加权进度** —— 避免「进度 50%」这种拍脑袋数字。水电占 15%、瓷砖占 12%，完成几项就是几项，客观可查。

3. **逾期自动计算而非人工标记** —— 节点状态里「已逾期」由计划日期与今天比较自动得出，杜绝项目经理把工期一拖再拖还不留痕。

4. **变更签证独立建模** —— 装修纠纷 80% 来自「这个要不要加钱」。独立实体 + 客户确认状态 + 金额留痕，是唯一有效解法。

5. **收款按合同分期而非按项目总额** —— 行业惯例是分段收款，做成计划表才能自动提醒、自动算逾期。

6. **演示数据全部动态生成日期** —— 基于「今天」偏移计算，保证任何时间打开都既有进行中的工地、也有逾期提醒，演示效果稳定。

7. **原生小程序而非框架** —— 装企 IT 能力普遍弱，交付物必须「用微信开发者工具打开就能跑」，零 npm、零构建、零配置。
